## Information integrity

- `src/data/realOpportunities.ts` is a manually researched official-source snapshot of European programmes and general lab-enquiry routes, not a promise of current vacancies. First checked 28 October 2026; statuses rechecked and records added 10 November 2026 (see the log in `docs/source-review.md`). Refresh statuses with `npm run status:report` and `docs/status-updates.md`; the report is read-only and must never change a status by itself.
- `src/data/opportunities.ts` contains six fictional fixtures, available only in the separate demo collection or saved records. Keep `isSample`, fictional institutions and no official application links.
- Preserve a record's named cycle. Closed historical records must not masquerade as next-year openings. A future deadline does not prove applications are open.
- Every real factual field has evidence: `source-checked`, `not-stated`, `not-checked`, `not-applicable`, or `unclear`, with the source URL, actual check date, and relevant notes. Source checks do not verify unrelated fields.
- Real records must use `defineRealOpportunity` with explicit evidence for every `factKeys` entry and matching dated sources. `src/lib/evidenceHelpers.ts` shortens entries but still requires the URL and actual date. Never restore automatic verification of populated values or a shared check-date default. `eligibilitySummary` is a sourced highlight, not the complete requirements; it appears as “Key restrictions” at the top of the detail page’s eligibility section. Catalogue cards are deliberately minimal at the user's request (10 Nov 2026): status, title, institution, country, deadline and funding only. Eligibility, topics and check dates live on the detail page.
- Never infer “no requirement” from null or missing information. Unknown GPA, documents, funding and eligibility must remain explicit.
- Do not invent exact times from date-only deadlines. Explain official-source contradictions rather than silently selecting a convenient answer.
- Category wording is exactly `Structured programme`, `Advertised position`, or `Speculative lab outreach`. `No advertised vacancy` is a separate application-status value, distinct from `Unknown`.
- General preparation tasks are guidance, not the provider's official document list. Apply through the official source only.

## State and architecture

Routes: `/`, `/opportunities`, `/opportunities/:slug`, `/saved`, and a catch-all recovery page. Route components access data through `opportunityRepository` in `src/lib/opportunities.ts`.

Keep all catalogue filters, collection, sort and hide-closed settings in URL query parameters. `useCatalogueQuery` keeps a synchronous query draft so same-render rapid updates accumulate. Filter changes create browser-history entries; typing replaces the current entry. POP navigation must update controls and results from the URL.

Detail links originating in a catalogue capture the complete URL and scroll position in router history state. Explicit Back links restore this context; direct visits fall back to the general catalogue. Never trust an external return URL. Preserve modified-click/new-tab link behaviour.

`DeviceProvider` owns versioned, validated localStorage data under `biointern-radar:device:v1`. Saved IDs and checklist task IDs are separate for each stable opportunity ID. Task IDs must remain stable. Support explicit checklist reset, blocked/corrupt storage warnings and cross-tab updates. Keep user data on the device; no account or network writes.

## Design and accessibility

The current visual direction (10 Nov 2026) is blue, with a light theme (white surfaces, navy text, blue accents) and a dark theme (deep navy, periwinkle accents), superseding the green and earlier graphite palettes at the user's request. Rounded shapes stay: pill controls and 24–30px card radii. Light is the default; dark follows the device setting unless the visitor picks one with the header sun/moon toggle (`src/lib/theme.ts`, stored separately under `biointern-radar:theme`). Stylesheets have one job each (consolidated 11 Nov 2026): `night-theme.css` holds only design tokens, each colour written once as `light-dark(light, dark)`; `styles.css` holds layout and every component, mobile-first, each selector defined once; `motion.css` holds all animation, entirely inside `prefers-reduced-motion: no-preference`; `sweep-radar.css` holds the radar. Never hard-code a colour outside `night-theme.css` and never add a second stylesheet that overrides another (`src/test/quality.test.ts` enforces the tokens). The production build uses Lightning CSS so `light-dark()` also works in pre-2024 browsers. Status colours stay semantic (Open green, Upcoming violet, Closed rose, Unknown amber). Card-to-detail navigation uses the View Transitions API where supported (`src/lib/viewTransition.ts`), with a plain fallback. Keep native type. Use restrained glow on the hero and radar, not body copy. The showpiece layer (11 Nov 2026, at the user's request) is decoration over the same content and must stay optional: a slow colour drift behind every page, a light that follows a mouse pointer across cards with a slight tilt (`src/lib/pointerLight.ts`; fine pointers only), scroll-driven reveals and a reading-progress bar (only inside `@supports (animation-timeline: view())`), a light sweep on the primary button, and hero facts that count up to their computed values (`CountUp` must always settle on the real number). None of it may change a fact, hide content from keyboards or screen readers, or run under reduced motion. Informational catalogue text is at least 12px; primary practical data is 14–16px. Labels and controls must remain readable, with 16px mobile inputs and select controls. Narrow-screen filters use a single column so long values fit.

Use the native Apple/system sans-serif stack without bundling or downloading SF Pro. Titles use strong weights (750–800), card titles 700 and body text a modest 450. Keep the overview concise: one introduction and primary action, three computed catalogue facts (record count, countries, latest source check; never typed by hand), the radar, featured records and brief application guidance. The header is sticky with pill navigation (active page tinted); DOM order is brand, menu button, navigation, theme toggle. The footer repeats the main links and the latest check date. Avoid decorative slogans and repeated captions; keep factual caveats available in disclosures.

Use semantic heading levels, labelled native controls, visible keyboard focus, skip navigation, live result counts, reduced-motion support and practical touch targets. Mobile visual sequence must match DOM order. Field labels in the home radar are real keyboard-accessible links. Mobile Show results collapses filters, scrolls to and focuses the result region.

The active homepage radar is `SweepRadar.tsx`: a five-second sweep, a gentle pulse and a bold, icon-free crossfading field name. Where WebGL works it is drawn in 3D (`helixScene.ts`, a hand-written point shader with no library: a DNA helix rising from a radar disc, reacting to the pointer and to scrolling, coloured from the theme tokens); the flat CSS radar stays in the page as the clock for each turn and as the fallback when WebGL is missing or the context is lost. No surrounding coloured tile or lower field strip. Cycle Genomics, Neuroscience, Molecular biology, Biotechnology and Bioinformatics. The current name is one real HTML link, held stable while focused. Next research field provides immediate manual access and pauses the sweep, including in reduced-motion mode. Sound is one site-wide, opt-in choice (`src/lib/sound.ts`, stored separately under `biointern-radar:sound`), switched from the radar or the footer: off by default, synthesised locally with no audio files, started only during a user gesture, with a ping once per completed turn and short cues for saving, checklist ticks and theme changes. Pause visual motion offscreen or when hidden; respect reduced motion. The earlier `three`-based renderer was deleted on 10 November 2026; do not add a 3D library or bundle models without a new request.
